Your business customers who have their own organizations in Kinde can set up single sign-on (SSO) for their team themselves. An admin in the organization opens the self-serve portal and follows a guided set up. It tells them what to create in their identity provider, tests the connection, and turns it on when they are ready.

This saves you going back and forth to exchange app credentials. Your customer is the identity provider for their users. You stay the service provider, and you keep control of the settings that affect your whole environment.

## Before an organization can set up SSO

Check these three things in Kinde. Until all three are in place, the organization can't start.

- Switch on **Enterprise SSO** in the [self-serve portal settings](/build/self-service-portal/self-serve-portal-for-orgs/), either for every organization or for [one organization](/authenticate/self-serve-sso/self-manage-sso-per-org/).
- Give the person setting it up a [role](/manage-users/roles-and-permissions/user-roles/) that includes the `org:read:authentication` and `org:write:authentication` permissions. With only the read permission they can see the organization's connections but can't set one up.
- Add the customer's email domain to the organization's verified domains (see below). A connection can only be set up for a verified domain.

### Add a verified domain to the customer organization in Kinde

A connection sends everyone who signs in with an email at its domain to the customer's identity provider. That is why an organization can only use domains you have verified for it.

1. Open the organization record in Kinde.
2. If prompted, in the **Activate advanced organization features** box, select **Activate**.
3. Go to **Policies** in the menu.
4. Switch on **Allow org members to be auto-added**. The **Verified domains** field only appears, and domains are only kept, while this is on.
5. In the **Verified domains** text field, add the customer's domain or domains. Add each on a new line. Make sure you include only the domain, e.g. `mybusiness.com` and not the full domain URL such as `http://www.mybusiness.com`.
6. Select **Save**.

Only add domains you trust are owned by this organization. A domain can be used by one connection in an environment, so the first organization to set up a connection for a domain holds it.

## Set up SSO in the self-serve portal (instructions for your customer)

Provide these instructions to the customer in case they need assistance.

Before they start, the customer needs:

- Admin access to their identity provider, e.g. Okta, Microsoft Entra ID, or Google Workspace.
- The email domain their team signs in with, e.g. `mybusiness.com`.

To start, go to the self-serve portal, select **SSO**, and select **Start set up**. If the organization already has a connection, select **Add connection** instead.

The set up has six steps. Select **Save and exit** at any point to leave and come back later.

### 1. Confirm domain

Enter the company domain. The step lists the domains approved for the organization, and starts with the ones that are free to use. Add each domain on a new line, then select **Next**.

If the step says no domains are approved for the organization yet, the domain has to be added in Kinde first. See [Add a verified domain](#add-a-verified-domain-to-the-customer-organization-in-kinde).

### 2. Choose provider

Select the service the team signs in with, then select **Next**. The options include Okta, Google Workspace, Microsoft Entra ID (SAML, OAuth 2.0, or WS-Fed), Cloudflare, and a custom SAML option for any other provider.

### 3. Set up in the identity provider

This step shows short instructions written for the provider that was chosen. For most providers there is also a button to open the provider's admin console in a new tab.

- **For a SAML provider**, copy the **Single sign-on URL (ACS URL)** and the **Audience URI (Entity ID)** into the new application in the identity provider. Kinde creates a signing certificate for the connection. Select **Download certificate** if the identity provider asks for one to verify sign-in requests.
- **For Microsoft Entra ID (OAuth 2.0 or WS-Fed)**, copy the **Redirect URI (callback URL)** into the new app registration.

When the application exists in the identity provider, continue to the next step.

### 4. Connect

Bring the identity provider's details back to Kinde.

- **For a SAML provider**, paste the **Metadata URL** from the identity provider, or upload the metadata XML file. Either works. The URL must be a public HTTPS URL, and the file can be up to 1MB.
- **For Microsoft Entra ID (OAuth 2.0 or WS-Fed)**, enter the **Microsoft Entra ID domain**, **Client ID**, and **Client secret**. The domain is the **Primary domain** shown on the Microsoft Entra ID **Overview** page for the tenant, e.g. `contoso.onmicrosoft.com`. It is not shown on the app registration.

Select **Continue to test**.

### 5. Test

Select **Test sign-in** and sign in through the identity provider with a real account from the team. The test opens in a new tab.

The test only checks that the identity provider sends a person back to Kinde. It doesn't sign anyone in to your app, it doesn't create or change any user, and it doesn't turn SSO on for anyone.

When the test passes, the step shows what the identity provider sent back as the **Email**, **First name**, **Last name**, and **User ID**. If one of these is empty on a SAML connection, the identity provider probably uses a different name for it. Select **Map attributes** and choose the right attribute from the list of what the test received.

Select **Continue** to go on. To carry on without testing, select **Skip the test for now**.

### 6. Turn on

Check the summary of the provider, the domains, and the test result. Enter an **IT contact email** for the person responsible for this connection, then select **Turn on single sign-on**.

From this point, anyone with an email address at the connection's domains is sent to the identity provider when they sign in.

Two things are worth doing straight after:

- Ask one colleague to sign in before telling everyone.
- Keep one admin on a password until you've confirmed it works.

## Leave a set up and come back to it

A set up that isn't finished stays on the **SSO** page in the portal with a **Set up incomplete** badge and its progress, e.g. **3/6 steps completed**. Nobody can sign in through it yet.

1. Go to the self-serve portal and select **SSO**.
2. Select the three dots menu on the connection card, and choose **Continue set up**.

A set up that is no longer needed can be deleted from the same menu.

## What happens to existing users

When SSO is turned on, people who already have an account in the organization keep it. The first time one of them signs in through the identity provider, Kinde emails them a one-time code to confirm the address is theirs. After they enter it, their existing account is moved onto the SSO connection. This applies to people who belong to this organization only. See [How existing users are matched](/authenticate/self-serve-sso/manage-self-serve-connections/#how-existing-users-are-matched) for the exceptions.

By default, their other ways of signing in (such as a password or an email code) are then removed, so SSO is the only way in. You can change this for new connections with the **Strict mode** default. See [Manage SSO connections added by customers](/authenticate/self-serve-sso/manage-self-serve-connections/).

People who don't have an account yet are added to Kinde and to the organization when they first sign in, unless you have changed the provisioning defaults.

## Change a connection after it is set up

1. Go to the self-serve portal and select **SSO**. Each connection shows whether it is enabled, when it was last used, and how many sign-ins it has had.
2. Select the three dots menu on the connection card, and choose **Edit**.
3. Make your changes and select **Save**.

To change the domains, select **Change domains** in the edit window. This opens the first step of the set up for that connection.

To change the identity provider, disable the connection first. Changing the provider clears the connection details that were entered, so the new provider is set up from the start.

## Enable or disable a connection

1. Go to the self-serve portal and select **SSO**.
2. Select the three dots menu on the connection card, and choose **Disable connection**. To enable it again, choose **Edit**, select **Enable for organization**, and select **Save**.

## Delete a connection

Make sure users can sign in another way before deleting a connection. This action can't be reversed.

1. Go to the self-serve portal and select **SSO**.
2. Select the three dots menu on the connection card, and choose **Delete connection**.
3. Confirm that you want to delete the connection.
