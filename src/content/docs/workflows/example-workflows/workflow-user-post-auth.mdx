Trigger: `user:post_authentication`

This trigger fires after the user has completed single factor authentication (e.g email + password or Google).

<Aside type="warning">

At this stage the user is not authorized - we have not checked organization access or carried out MFA.

</Aside>

## Example use cases

### Minimize account sharing

Check previous logins by the user to see if they have carried out impossible travel or if their IP address looks suspicious. [Example code](https://github.com/kinde-starter-kits/workflow-examples/blob/main/postUserAuthentication/impossibleTravelWorkflow.ts)

### Add properties to a user

Add additional properties to a user before tokens are generated.

### Add user to organizations

If the user has been invited to join multiple organizations you can add them as this point, before going through the authorization flow.

### Determine if the user is a first time user

Users can be created in multiple ways (imported / API / via the UI / self-registration). This could well be an existing user in your own database, so we tell you if this is a new user from a Kinde perspective. i.e we create a new record so you can act accordingly. [Example code](https://github.com/kinde-starter-kits/workflow-examples/blob/main/postUserAuthentication/syncNewUserToHubspotWorkflow.ts)

## Sign-ins that start from a SAML application

If you use Kinde as a SAML identity provider ([workforce identity](/workforce-identity/)), this trigger also fires when a user signs in to Kinde to open a [SAML application](/workforce-identity/add-saml-application/). The workflow runs after the user authenticates and before Kinde returns them to the application.

The workflow only runs when the user actually signs in. If they already have an active Kinde session, Kinde sends the SAML assertion to the application without asking them to sign in, and the workflow does not run. Don't expect a workflow run for every request the service provider sends to Kinde.

How often users sign in depends on the application's [session settings](/workforce-identity/add-saml-application/#control-how-often-people-must-sign-in):

- When **Force re-authentication** is on, users sign in every time they open the application, so the workflow runs every time.
- When it is off, a signed-in user is only asked to sign in again once the application's **Session lifetime** has passed since they last signed in. The workflow runs at that sign-in.

The `clientId` values in the event are the client ID of Kinde's self-serve portal application, not an ID for the SAML application. Sign-ins to the self-serve portal itself use the same client ID, and nothing else in the event identifies the SAML application. Keep this in mind if your workflow branches on client ID.

Workflows can't change the SAML assertion Kinde sends to the application. See [SAML applications](/workflows/example-workflows/user-token-generation/#saml-applications).

The main argument provided to your code is the Kinde workflow `event` object which has two keys `request` and `context`. This gives you access to the reason the workflow was triggered and additional relevant datapoints. Here's an example:

### Example workflows

See examples on GitHub:

- [Sync new user data to Hubspot](https://github.com/kinde-starter-kits/workflow-examples/blob/main/postUserAuthentication/syncNewUserToHubspotWorkflow.ts) - Send user data and UTM tags to Hubspot when a new user record is created in Kinde.
- [Impossible travel - Trustpath integration](https://github.com/kinde-starter-kits/workflow-examples/blob/main/postUserAuthentication/impossibleTravelWorkflow.ts) - Evaluate user login risk using TrustPath's API by checking for "impossible travel" patterns based on IP and recent login activity. If high risk is detected, access is blocked proactively.
- [Sync user attributes and groups from a SAML assertion into Kinde with user properties](https://github.com/kinde-starter-kits/workflow-examples/blob/main/postUserAuthentication/syncAttributesSamlWorkflow.ts). This works with any SAML connection, as long as attributes and groups are exposed in the SAML response. Use this to sync user attributes with Kinde, and to do one-way syncs from IdP to Kinde.
